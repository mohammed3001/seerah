# Security Policy

Seerah ("the Project") takes the security of its users' resume data, payment
information, and admin tooling seriously. This document explains how to
report a vulnerability and what to expect after you do.

If your discovery affects the runtime production system rather than the
source-tree security posture, please prefer private disclosure (below) over a
public GitHub issue or pull request.

## Reporting a vulnerability

Send a private report to **security@seerah.com** with as much of the
following as you can produce:

- A description of the vulnerability and its impact (e.g. "any authenticated
  user can read another user's resume rows" → confidentiality / IDOR).
- Steps to reproduce, ideally with a curl invocation, a screenshot, or a
  short video.
- The affected URL, file, or migration where the bug originates.
- Any logs, stack traces, or error responses you collected.
- Optionally, a suggested fix.

If you do not have a way to email us privately, you may open a
[GitHub Security Advisory](https://docs.github.com/en/code-security/security-advisories)
on this repository. **Do not file a regular GitHub issue or pull request
that exposes the vulnerability** until we have shipped a fix.

## What to expect

- **Within 48 business hours:** we will acknowledge receipt and create a
  tracking issue (private, in the repo's security advisories panel).
- **Within 7 days:** we will respond with an initial assessment — whether
  we can reproduce the issue, our preliminary severity rating, and the
  expected timeline for a fix.
- **Within 30 days for high-severity issues, 90 days for lower-severity
  issues:** we will ship a fix to production, after which you are welcome
  to publicly disclose the issue (we will coordinate the wording with you).

We do not currently operate a paid bug-bounty program, but we will credit
your finding in the changelog and the resolved security advisory if you
wish.

## In scope

- The Next.js web app at `seerah.com` and the admin panel at
  `admin.seerah.com`.
- The mobile Flutter app distributed via the App Store and Play Store.
- The FastAPI services under `services/ai` and `services/pdf`.
- Anything in `supabase/migrations/` that affects authentication, RLS, or
  data isolation.
- Build artefacts produced by this repo's CI.

Examples of issues we are actively interested in:

- IDOR / privilege-escalation bugs on resume, profile, subscription, or
  support-ticket endpoints.
- Authentication bypass, session-fixation, or 2FA-replay bugs in either the
  consumer auth flow or the admin auth flow.
- Cross-tenant data leaks (e.g. a Hive-cache leak between two users on the
  same mobile device — see [`docs/audit/M1b-emulator-verification.md`](docs/audit/M1b-emulator-verification.md)).
- File-upload bugs that bypass the magic-byte image validator in
  `packages/api/src/security/image-validation.ts`.
- SSRF / open-redirect on `services/pdf` (the renderer fetches user-supplied
  CSS/image URLs).
- Storage bucket misconfiguration that leaks private resume PDFs.
- Stripe / Paddle webhook authentication bypass.
- Server-side template injection in the resume render pipeline.
- Subdomain takeover on `*.seerah.com`.

## Out of scope

The following are knowingly accepted risks or design decisions; please do
not file reports about them unless you have new information that changes
the threat model.

- **Certificate pinning is intentionally absent.** Supabase rotates its
  TLS certificates, and the operational pain of pinning outweighs the
  added MITM protection over the system trust store.
- **Jailbreak / root detection is intentionally absent** on the mobile
  app. False-positive rate is high and the controls are easy to bypass
  for a determined attacker.
- **Self-XSS** that requires the victim to paste attacker-supplied content
  into their own browser console.
- **Missing security headers on third-party domains** we don't control
  (Supabase, Stripe, Paddle, Sentry, PostHog).
- **Rate-limit absence on endpoints currently slated for the `S2` audit
  PR** — this is tracked in [`docs/audit/X1-final-report.md`](docs/audit/X1-final-report.md)
  §4 and is awaiting external secrets.
- **Lack of CSP nonce** on Next.js scripts — the migration is documented
  in `X1-final-report.md` §5 and gated on Sentry (`S6`) landing first.
- **Reports generated by automated scanners with no manual triage** (e.g.
  raw `nuclei` or `nikto` output without a working PoC).
- **Stack traces in 500 responses on non-production environments** —
  development surfaces are intentionally verbose.

## Responsible disclosure

We will not pursue legal action against researchers who:

- Disclose privately first and give us a reasonable window to fix.
- Do not exfiltrate, modify, or destroy other users' data.
- Do not run denial-of-service attacks against production.
- Do not access or modify other users' accounts beyond what is strictly
  necessary to demonstrate a vulnerability (and immediately back out
  afterwards).

Thank you for helping keep Seerah safe.
